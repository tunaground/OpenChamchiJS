# 스레드 웹 푸시 알림 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 로그인 사용자가 스레드를 알림 등록하면, 브라우저를 닫았거나 다른 앱이나 탭을 보고 있어도 새 답글 소식을 Web Push로 받는다.

**Architecture:**
- 저장소 구성: Prisma에 `ThreadWatch`와 `PushSubscription` 테이블을 추가하고 `GlobalSettings`와 `User`에 필드를 추가한다. 등록 관리와 기기 구독은 기존 service/repository DI 패턴을 따른다.
- 발송 흐름: 답글 생성 API가 `after()`로 notifier를 호출한다. notifier는 SQL 한 번으로 쿨다운과 대상 선점을 원자적으로 처리하고 `web-push`로 발송한다.
- 클라이언트: 서비스 워커(`public/sw.js`), Zustand 스토어, TopBar 🔔 드롭다운, 스레드 사이드바 버튼, 보는 중 하트비트 훅으로 구성한다.

**Tech Stack:** Next.js 16 App Router (`after` from `next/server`), Prisma 7 (PostgreSQL), NextAuth 4, `web-push`, Zustand 5, styled-components, next-intl, Jest(ts-jest, node env)

**Spec:** `docs/superpowers/specs/2026-10-23-web-push-design.md`

## Global Constraints

- 기능 활성 조건: `pushWatchLimit > 0` && `vapidPublicKey` && `vapidPrivateKey` && `vapidSubject`. 하나라도 빠지면 발송, 등록, 하트비트가 모두 동작하지 않는다. UI(🔔, 등록 버튼)도 렌더링하지 않는다.
- `pushWatchLimit` 기본값은 **0**이다. 상한은 개별 off 등록까지 포함해서 센다. 가득 차면 거부한다(밀어내기 없음). n을 줄여도 기존 등록은 유지한다. n = 0이 되어도 레코드는 보존한다.
- 쿨다운은 사용자×스레드당 **60초**다. 쿨다운 중에 들어온 답글은 무시한다(지연 발송 없음).
- 보는 중 판정은 `lastViewingAt`이 **45초** 이내인 경우다. 하트비트는 visible 상태에서 **30초** 간격으로 보낸다.
- 전체 off(`User.pushEnabled`)와 개별 off(`ThreadWatch.enabled`)는 독립적으로 저장한다. 발송 조건은 둘 다 true인 경우다.
- 자기가 쓴 답글로는 자기에게 발송하지 않는다(`userId` 기준).
- 같은 스레드 알림은 `tag: "thread-{threadId}"`, `renotify: true`를 쓴다.
- 제거는 **하드 삭제**다. `ThreadWatch`와 `PushSubscription`의 `user` 관계는 `onDelete: Cascade`다.
- 푸시 응답이 404/410/401/403이면 해당 기기 구독을 삭제한다. 그 밖의 오류는 `console.error`만 남긴다.
- 푸시 TTL은 3600초, urgency는 `"normal"`이다.
- VAPID 비밀키는 어떤 API 응답에도 포함하지 않는다.
- 상태 변경 API는 로그인 필수이고 `validateOrigin()`을 거친다.
- 모든 UI 문구는 ko/en/ja 3개 파일에 같은 키로 추가한다.
- **커밋은 마지막 Task에서 한 번만 한다.** 각 Task 안에서는 커밋하지 않는다(사용자 규칙). 커밋 전에 CHANGELOG `[Unreleased]`를 갱신한다.

## Review Focus

1. **동시에 들어온 답글 두 개**: 같은 사용자에게 푸시는 정확히 한 번만 나가야 한다. 쿨다운 선점이 `UPDATE ... RETURNING` 한 문장으로 원자적인지 확인한다. Task 4 테스트는 SQL 조건을 고정하지 못하므로 리뷰어가 쿼리를 직접 읽는다.
2. **공용 브라우저**: A가 구독한 뒤 로그아웃하고 B가 로그인해서 구독하면, 해당 endpoint의 소유자는 B여야 한다. A에게 오는 알림이 B의 기기로 가면 안 된다. Task 3의 `subscribe` 테스트로 고정한다.
3. **n을 줄였거나 0으로 바꾼 뒤**:
   - n을 줄인 경우: 기존 등록 목록 조회와 토글, 제거는 계속 동작해야 한다. 막히는 건 새 등록뿐이다.
   - n = 0인 경우: 모든 API가 `FEATURE_DISABLED`를 반환하되 데이터는 남아 있어야 한다.
   - Task 2와 Task 5 테스트로 고정한다.
4. **삭제된 스레드**:
   - 등록 목록에는 "삭제된 스레드"로 남아 사용자가 직접 제거할 수 있어야 한다.
   - 발송 대상에서는 빠져야 한다.
   - 이미 삭제된 스레드에 새로 등록하려 하면 NOT_FOUND를 반환한다.
   - Task 2 테스트로 고정한다.
5. **알림 권한 거부 / iOS 비설치**:
   - "알림 받기"를 눌렀는데 권한이 거부됐거나 `PushManager`가 없으면, 스레드 등록을 하지 않고 안내 문구를 보여준다.
   - 반쪽 상태(구독은 없는데 등록만 되어 있음)를 만들지 않는다.
   - Task 6 `ensureDeviceSubscribed`가 `"denied" | "unsupported"`를 반환하면 등록 요청을 보내지 않는 것으로 고정한다.

    interface ThreadWatchRepository {
      findActiveByUser(userId: string): Promise<ThreadWatchListItem[]>;   // createdAt asc, thread join
      findByUserAndThread(userId: string, threadId: number): Promise<{ id: string; enabled: boolean } | null>;
      countByUser(userId: string): Promise<number>;
      createWithinLimit(userId: string, threadId: number, limit: number): Promise<"created" | "exists" | "limit">; // 트랜잭션 안에서 count → create, P2002는 "exists"

      setEnabled(id: string, enabled: boolean): Promise<void>;
      delete(id: string): Promise<void>;
      deleteByUserAndThread(userId: string, threadId: number): Promise<void>;
      setViewing(userId: string, threadId: number, at: Date | null): Promise<void>; // updateMany, 없으면 no-op
      getUserPushEnabled(userId: string): Promise<boolean>;
      setUserPushEnabled(userId: string, enabled: boolean): Promise<void>;
    }
    interface ThreadWatchService {
      list(userId: string): Promise<{ items: ThreadWatchListItem[]; limit: number; pushEnabled: boolean }>;
      watch(userId: string, threadId: number): Promise<void>;
      unwatchThread(userId: string, threadId: number): Promise<void>;
      remove(userId: string, watchId: string): Promise<void>;
      setEnabled(userId: string, watchId: string, enabled: boolean): Promise<void>;
      setPushEnabled(userId: string, enabled: boolean): Promise<void>;
      reportViewing(userId: string, threadId: number, viewing: boolean): Promise<void>;
    }
    export function createThreadWatchService(deps: { threadWatchRepository; threadRepository; globalSettingsService }): ThreadWatchService
    export const threadWatchService
    ```
  - 모든 메서드는 처음에 `isPushFeatureEnabled(await globalSettingsService.get())`을 검사한다. false면 `FEATURE_DISABLED`를 throw한다. 단 `reportViewing`은 throw 없이 조용히 return한다.

- [ ] **Step 1: 실패하는 테스트 작성** (thread-ban.test.ts와 같은 mock 팩토리 스타일). 각 테스트명과 기대값:
  - `watch rejects when feature disabled (limit 0)` → `FEATURE_DISABLED`, `createWithinLimit` 미호출
  - `watch rejects deleted or missing thread` → `threadRepository.findById`가 `{deleted:true}` 또는 null을 반환하면 `NOT_FOUND`
  - `watch passes settings limit to repository` → `createWithinLimit("u1", 1, 10)` 호출
  - `watch throws WATCH_LIMIT_EXCEEDED when repository returns "limit"`
  - `watch is idempotent when repository returns "exists"` → resolve
  - `remove rejects another user's watch` → `findById`가 `{userId:"other"}`를 반환하면 `NOT_FOUND`, `delete` 미호출
  - `setEnabled updates only that watch` → `setEnabled("w1", false)`
  - `setPushEnabled(false) does not touch per-watch enabled` → `setUserPushEnabled("u1", false)` 호출, `setEnabled` 미호출
  - `list returns items, limit and pushEnabled, and still works when count exceeds limit` → limit 2에 item 3개면 그대로 3개 반환
  - `reportViewing(true) sets now, (false) sets null`, `reportViewing is a silent no-op when feature disabled`
- [ ] **Step 2: 실패 확인** — Run: `npm test -- --testPathPattern=thread-watch`. Expected: FAIL
- [ ] **Step 3: 인터페이스, prisma 구현, 서비스 구현**
  - `createWithinLimit`는 `prisma.$transaction(async tx => { count; if (count >= limit) return "limit"; create })` 구조로 만든다. 고유 제약 위반 `P2002`는 `"exists"`로 변환한다. 이미 등록된 경우는 count보다 먼저 `findUnique`로 확인해서 `"exists"`를 반환한다. 그래야 가득 찬 상태에서 이미 등록한 스레드를 다시 눌러도 limit 오류가 나지 않는다.
- [ ] **Step 4: 통과 확인** — Run: `npm test -- --testPathPattern=thread-watch`. Expected: PASS
